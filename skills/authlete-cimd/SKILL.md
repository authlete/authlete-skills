# Add CIMD to your Authlete server

**What this adds:** clients that identify themselves with an `https://` URL instead of a registered
client ID. The URL serves the client's metadata as JSON (name, redirect URIs, auth method). MCP clients
such as Claude Code and VS Code work this way, and the MCP authorization spec recommends it over
Dynamic Client Registration.

Like DPoP, CIMD is **not a new endpoint**. It is service configuration on top of the endpoints you
already have.

## How it works (the short version)

When `/oauth/authorize` receives a `client_id` that is a URL Authlete has not seen, **Authlete**
fetches the document, validates it, registers the client and caches it for up to a day, all inside
the normal authorization call. **You** forward the raw request, as the base server already does.
Nothing in your code changes.

## Before you start

1. **Authlete access.** Check that the server's config has `AUTHLETE_BASE_URL`, `AUTHLETE_SERVICE_ID`
   and a Service Access Token (names only: never read or print `.env` files). If the user has none,
   they create them; you cannot create accounts or handle tokens. Give them these steps and wait:
   1. Sign up at https://console.authlete.com/register.
   2. **Services** → **Create Service**: pick an **API Cluster** (US, JP, EU, BR) and a name. Use a
      test service.
   3. **Service Settings**: note the **Service Identifier**. **Create Token** with the **Authorization
      Server** preset, and copy it (shown once).
   4. Put the values in the server's environment, and do not paste the token into the chat.

   Then confirm access with a read-only call, without printing the token:
   `curl -s "$AUTHLETE_BASE_URL/api/$AUTHLETE_SERVICE_ID/service/configuration" -H "Authorization: Bearer $TOKEN" | jq .issuer`
   (a string means it works).
2. **A server.** If there is no authorization server yet, generate one with
   [authlete-oauth-server](../authlete-oauth-server/SKILL.md) first. If there is one, map it (next
   section) before changing anything.
3. **Ask:** "Are you setting this up so MCP clients, such as Claude Code, can sign in to your MCP
   server?" If yes, also do Step 3.
4. **Confirm the plan** with the user, and ask which client ID URLs to allow (Claude Code:
   `https://claude.ai/oauth/claude-code-client-metadata`). If the service serves production traffic,
   say so and ask again before changing it.

## Map an existing server

Skip this for a server generated by `authlete-oauth-server`. For any other server, understand it
before changing it. Search by routes and calls, not by file names:

| Find | Look for |
|---|---|
| Framework and routing | The entry file, router setup, route registrations |
| The OAuth endpoints | Routes for authorize, token, discovery, introspection or userinfo, whatever they are named |
| Who does the protocol work | The Authlete SDK and its calls (`processRequest`, `ProcessRequest`, `process_request`); or a library such as node-oidc-provider or Spring Authorization Server; or hand-written code |
| Where clients live | A database table, a config file, the library's store |
| How users log in | The session, login page and user store |
| How tokens are issued and checked | Signing keys, a token table, middleware on the APIs |

Then show the user the mapping before touching code, for example:
"`/oauth/authorize` in `src/auth/routes.ts` → Authlete `auth/authorization`. Login stays in
`src/auth/login.ts`. Clients move from the `oauth_clients` table to Authlete."

- **Already on Authlete:** this is the CIMD change. Continue with Step 1, then Step 2.
- **A library or hand-written OAuth:** this is a migration to Authlete, not a feature, because
  Authlete only handles CIMD for requests it processes.
  - **Keep:** routes, login, sessions, the user store and the consent screen. Authlete never replaces
    login.
  - **Replace:** the protocol logic inside authorize and token with Authlete calls, the client store
    with Authlete clients, and token issuing and checking with Authlete (APIs switch to
    introspection).
  - **Say what breaks** and get an explicit yes: existing clients must be created in Authlete,
    existing tokens stop working unless both systems run side by side for a while, and the token
    format may change for any API that reads tokens itself.
  - Change **one endpoint at a time**, following the handler shape in
    [authlete-oauth-server's contract](../authlete-oauth-server/reference/contract.md), and check
    each against [`conformance/spec.md`](conformance/spec.md) before the next.

## Step 1 — configure the service (this is the whole change)

`POST /api/{serviceId}/service/update` **replaces the whole service**: read it with
`GET /api/{serviceId}/service/get`, change only these fields, and send everything back. A partial
body resets the rest, including the service name.

| Field | Value | Why |
|---|---|---|
| `clientIdMetadataDocumentSupported` | `true` | The switch. Off by default. Discovery then advertises `client_id_metadata_document_supported` |
| `cimdAllowlistEnabled`, `cimdAllowlist` | `true`, the allowed client URLs | Without it, anyone can register by hosting a document |
| `supportedTokenAuthMethods` | add `NONE` | CIMD clients are public. Without it: `[A505306]` |
| `supportedGrantTypes` | add every grant type the allowed clients list | One unsupported value rejects the document: `[A505307]`. VS Code lists `DEVICE_CODE` |
| `pkceRequired`, `pkceS256Required` | `true` | Public clients have no secret, so PKCE protects the code |
| `accessTokenDuration` | greater than `0` | The default `0` issues tokens that are already expired |
| `issuer`, `authorizationEndpoint`, `tokenEndpoint` | your server's public URLs | Discovery has `null` endpoints until they are set |
| `httpAliasProhibited` | `true` | A client ID alias equal to a URL would shadow CIMD |
| `loopbackRedirectionUriVariable` | `true` for MCP | Claude Code registers `http://localhost/callback` without a port, then uses a random port. Without it: `[A011317]` |
| `supportedScopes` | add `mcp:tools` for MCP | The scope the MCP server checks |

Read the service back and confirm `clientIdMetadataDocumentSupported` is `true`.

Development-only switches, off by default: `cimdAlwaysRetrieved` (fetch on every request),
`cimdHttpPermitted` (`http://` client IDs), `cimdQueryPermitted` (query strings). To narrow what
clients may declare instead of widening the service, use `cimdMetadataPolicyEnabled` with
`cimdMetadataPolicy`, a JSON **string** in OpenID Federation policy grammar.

## Step 2 — check the endpoints

**Base server:** nothing to change. It already serves discovery verbatim, passes raw parameters and
forwards client credentials. Go to Verify.

**Any other Authlete server:** keep its structure and fix handlers in place, only where:

- `/authorize` decodes, parses or validates `client_id` before calling Authlete. It is a
  percent-encoded URL: pass the query string unchanged.
- A handler looks clients up in a local table first. A CIMD client exists only in Authlete.
- A handler branches on `resultCode`, rewrites `responseContent`, or misses an action
  (`INTERACTION`, `NO_INTERACTION`, `LOCATION`, `FORM`, `BAD_REQUEST`, `INTERNAL_SERVER_ERROR`).
- `/token` rejects requests without client credentials. CIMD clients send `client_id` and
  `code_verifier`, no secret.
- Discovery is built by hand and lacks `client_id_metadata_document_supported`.

While there, check the server follows Authlete's model: `NO_INTERACTION` (for example `prompt=none`)
calls `issue` if the user has a session, otherwise `fail` with `reason: NOT_LOGGED_IN`; tickets are
single-use, expire after 24 hours, and never reach the browser; the `subject` is a stable internal ID
(not an email), at most 255 printable ASCII characters. See
[Request and Response](https://developers.authlete.com/get-started/concepts/request-and-response.md),
[Action Handling](https://developers.authlete.com/get-started/concepts/action-handling.md),
[Two-Step API Calls](https://developers.authlete.com/get-started/concepts/two-step-api-calls.md) and
[Subject](https://developers.authlete.com/get-started/concepts/subject.md).

## Step 3 — MCP servers (optional)

The MCP server is the resource server. It never issues tokens; it tells clients where to get one and
checks each token.

1. **Protected resource metadata** (RFC 9728) at `/.well-known/oauth-protected-resource`, and at
   `/.well-known/oauth-protected-resource/<path>` when the MCP endpoint has a path:
   `{ "resource": "<MCP URL>", "authorization_servers": ["<issuer>"], "scopes_supported": ["mcp:tools"], "bearer_methods_supported": ["header"] }`.
   `authorization_servers` must hold the service's `issuer`.
2. **401 without a valid token**, with
   `WWW-Authenticate: Bearer resource_metadata="<metadata URL>", scope="mcp:tools"`. This header is
   how a client finds your authorization server.
3. **Introspect every request** with Authlete's `auth/introspection`, passing `token`,
   `scopes: ["mcp:tools"]` and `resources: ["<MCP URL>"]`. `OK` → serve (`subject` is the user,
   `metadataDocumentLocation` is the client's URL); `UNAUTHORIZED` → 401 with the header;
   `FORBIDDEN` → 403; `BAD_REQUEST` → 400. Never pass the token on to other APIs.

SDK calls: TypeScript `introspection.process`, Go `Introspection.Process`, Ruby
`introspection.process_request`.

4. **Connect a client.** `claude mcp add --transport http <name> <MCP URL>`, then run `/mcp` in Claude
   Code and choose **Authenticate**. The browser opens your login page; after the user approves, tool
   calls succeed.

## What you don't build

Fetching, validating, registering and caching the client's document; checking the redirect URI
against it; enforcing PKCE. Authlete does all of it inside the calls you already make.

## Rules

- Never handle credentials: no accounts, no tokens in chat, no reading `.env`.
- Never send a partial service update.
- Never enable CIMD on a production service without an allowlist.
- Never invent field names, console paths or result codes. Fetch the docs below or say so.
- Never restructure an existing server. Change handlers in place.
- Never set a client ID alias to a URL. It shadows the CIMD URL.
- Read `metadataDocumentLocation` from `client` in authorization responses. The top-level field is
  `null` there.

## Errors

| Code | Cause | Fix |
|---|---|---|
| `A505301` | Authlete could not fetch the document | Make it publicly reachable over `https` |
| `A505308` | The document or URL failed validation, for example a URL over 200 characters | Fix the document or shorten the URL |
| `A505306` | The service does not support the document's `token_endpoint_auth_method` | Add `NONE` |
| `A505307` | The service does not support a declared value, usually a grant type | Add it, or drop it with a metadata policy |
| `A011317` | The `redirect_uri` is not in the document | Use a listed URI; for portless `localhost`, set `loopbackRedirectionUriVariable` |
| `A050305` | The code does not exist or was used | Restart the flow |
| `A050315` | The `code_verifier` does not match | Send the verifier from the same flow |
| `A057302` | The access token does not exist | 401 |
| `A286301`, `A286303` | The token lacks the scope, or was issued for another resource | 403 |

Document changes take effect after the cache expires (up to a day).

## Before going live

Keep the allowlist on, leave the development switches off, and replace the base server's demo login
with real authentication.

## Verify it works

Run [`conformance/spec.md`](conformance/spec.md). It uses a public test client,
`https://makeclient.dev/oauth/client-metadata.json`; add it to the allowlist for the test. The most
telling check: the test client's URL reaches the login page and ends with a token, though nobody
registered it, and the client then appears on the service's **Clients** page with source
`METADATA_DOCUMENT`.
